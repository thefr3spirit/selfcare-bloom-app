# SelfCare Together (Selfcare & Bloom)

Flutter app for stress management / mental health pilot study (Uganda/Kenya). Offline-first (Hive local storage) with Firebase for auth and push notifications. Ships to both Android and iOS (bundle id `com.selfcarebloom.app`).

**No cloud sync/backup**: `cloud_firestore`/`cloud_functions` were removed (2026-09-04) — they pull in a gRPC/abseil/leveldb/nanopb C++ dependency chain that App Store Connect rejects at upload validation with "No architectures in the binary" (409, `STATE_ERROR.VALIDATION_ERROR`). Confirmed via bisection: a minimal throwaway Flutter app uploaded fine with Firebase Auth/Messaging/Google/Apple Sign-In, but reproduced the exact error the moment `cloud_firestore`/`cloud_functions` were added — everything else (architecture, signing, entitlements, checksums) was always fine. `lib/services/firestore_service.dart`, `notification_analytics_service.dart`, and the Firestore-touching parts of `firebase_service.dart`/`firebase_push_service.dart` are now no-op stubs (same public API, so callers didn't need to change) rather than deleted, in case a fix or workaround surfaces later (e.g. a future Firebase iOS SDK release, or a non-gRPC Firestore transport).

This directory (`selfcare_app/`) is the actual Flutter project and git repo root — everything above it (`D:\SelfCareTogether\`) is research/analysis material for the underlying study, not part of the app.

Repo: `https://github.com/thefr3spirit/selfcare-bloom-app` (branch `main`).

## Cross-device workflow

Development happens on this Windows PC. iOS builds **used to** happen on a cousin's Mac, but that access is gone as of 2026-08-18 — there is no Mac in the loop anymore.

**iOS builds now happen via GitHub Actions** (`.github/workflows/ios-testflight.yml`), triggered manually (`workflow_dispatch` — every run attempts a real App Store Connect upload and consumes a build number, so it doesn't run on every push). It uses a hosted macOS runner + an App Store Connect API key for automatic signing (`xcodebuild -allowProvisioningUpdates -authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID`), so nothing needs to be exported from the old Mac's keychain. Required repo secrets: `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_API_KEY_P8` (the raw `.p8` contents) — generate the key at App Store Connect → Users and Access → Integrations → App Store Connect API (Admin role), no Mac required. **This workflow has been run successfully end-to-end** (as of 2026-09-04) — Archive, Export, and `fastlane pilot upload` to TestFlight all completed with a real, confirmed "Successfully uploaded the new binary to App Store Connect."

**GitHub CLI (`gh`) is installed** at `C:\Program Files\GitHub CLI\gh.exe` and authenticated as `thefr3spirit` (installed 2026-09-04 via `winget install --id GitHub.cli`, not on Windows PATH by default in Git Bash — add `export PATH="/c/Program Files/GitHub CLI:$PATH"` first, or use the full path). Use it to trigger runs (`gh workflow run ios-testflight.yml`), pull full logs directly (`gh run view <id> --log --repo thefr3spirit/selfcare-bloom-app`) and grep them, and download build artifacts (`gh run download <id> -n ios-build-output`) — this is far more reliable than GitHub's web log viewer, which truncates large logs and can't be searched precisely. `gh run watch <id> --exit-status` works but its interactive TUI refresh has been observed getting killed by the harness on long-running background waits; a plain polling loop (`until [ "$(gh run view <id> --json status -q .status)" = "completed" ]; do sleep 20; done`) or `ScheduleWakeup` check-ins are more reliable for waiting on a run.

**A separate diagnostic workflow exists**: `.github/workflows/ios-diagnostic-test.yml` builds a disposable, minimal `flutter create` app (bundle ID `com.selfcarebloom.diagtest`, its own App ID + App Store Connect app record already set up in the Apple Developer Portal / App Store Connect) through the same archive → export → upload pipeline. It's what proved the "No architectures in the binary" bug was caused by `cloud_firestore`/`cloud_functions`, by adding dependencies incrementally until the error reproduced. Keep it around — it's the fastest way to re-isolate any future upload-validation regression without burning a real build number on the actual app, and without waiting through the real app's much longer CocoaPods/gRPC-adjacent build.

**Codemagic CI was tried once before and abandoned** (failed on an SPM build-flag error, before most of the current Podfile fixes existed). GitHub Actions was chosen instead because the repo is public, so macOS runner minutes are free/unmetered (Codemagic's free tier is capped). If the GitHub Actions workflow also turns out to be unworkable, that's the fallback to reconsider — but try to fix the workflow first.

Bump `pubspec.yaml`'s build number (`+N` after `1.0.0`) past whatever Apple last reviewed before triggering a new upload — Apple rejects re-uploads at or below an already-seen build number. Check the last rejection email's "Version reviewed" line if unsure.

## iOS build/signing

- `CODE_SIGN_STYLE = Automatic` in `ios/Runner.xcodeproj/project.pbxproj`, team `C26VK7Y2WB`.
- `ExportOptions.plist` at the repo root (`signingStyle: automatic`, `method: app-store`) was what the Mac used to archive/export interactively — kept for reference / possible future manual use, but nothing currently reads it.
- `ios/ExportOptions-ci.plist` is what the GitHub Actions workflow actually uses — `method: app-store`, no `destination: upload` (exports a local, inspectable `.ipa`; upload happens as its own separate step via `fastlane pilot upload`, not folded into `xcodebuild -exportArchive`).
- **Apple requires the iOS 26 SDK (Xcode 26+) to upload at all**, confirmed via a real "SDK version issue... must be built with the iOS 26 SDK or later" rejection when archived with `macos-15`'s default Xcode 16.4. The workflow sets `DEVELOPER_DIR: /Applications/Xcode_26.3.app/Contents/Developer` at the job level (that Xcode version already exists side-by-side on the `macos-15` runner image — no need to switch runner images or use `macos-latest`).
- `ios/Podfile` has a heavily-customized `post_install` block — strips embedded provisioning profiles from frameworks, patches `set -u` scripts, injects `Info.plist` into `Flutter.framework` for Xcode 26+, and (as of 2026-09-04) whitelists `Runner.app/Frameworks/` to only `*.framework`/`*.dylib`/`*.bundle` entries (`CM_WHITELIST_FRAMEWORKS_DIR`) — a CocoaPods/Xcode embed-script bug can `ditto` the *entire* `ios/` source directory (Podfile, Pods/, the unprocessed `Runner/Info.plist` template with literal un-substituted macros, etc.) into `Frameworks/`, confirmed by directly inspecting a real shipped IPA. Don't simplify/remove any of these without understanding why each exists (see git log for the individual `fix:` commits).
- `ITSAppUsesNonExemptEncryption = false` is set in `ios/Runner/Info.plist` to skip the export-compliance prompt (app only uses standard TLS).
- **Certificate exhaustion is a recurring, expected issue, not a one-off**: GitHub Actions runners are ephemeral — every run starts with an empty keychain, so `-allowProvisioningUpdates` often can't reuse a previous run's private key and generates a brand-new Apple Distribution certificate instead. This fills the account's certificate limit after enough CI runs. Symptom: Archive fails with "Choose a certificate to revoke. Your account has reached the maximum number of certificates." Fix (expect to repeat this periodically): Apple Developer Portal → Certificates, IDs & Profiles → Certificates → revoke old/duplicate Apple Distribution certs, keep only the most recent one or two.

## Authentication

Four sign-in methods: email/password, Google, **Apple**, and anonymous. Apple Sign-In was added because App Store review rejected the app under Guideline 4.8 for offering Google sign-in without an Apple equivalent.

- Implementation: `lib/services/firebase_service.dart` (`signInWithApple`, `deleteAppleAccount`, plus the pre-existing Google/email/anonymous equivalents). Apple uses the standard secure-nonce flow (`sign_in_with_apple` package + Firebase `OAuthProvider('apple.com')`).
- Capability: `ios/Runner/Runner.entitlements` (`com.apple.developer.applesignin`), wired into all 3 build configs via `CODE_SIGN_ENTITLEMENTS`.
- External config (already done, don't redo): Sign In with Apple capability enabled on the App ID in Apple Developer Portal; Apple provider enabled in Firebase Console → Authentication.
- Apple's sign-in button only renders on iOS (`Platform.isIOS` check) in `lib/screens/auth/login_screen.dart` and `register_screen.dart`.

**Gotcha:** account deletion is implemented independently in *two* screens — `lib/screens/profile_screen.dart` and `lib/screens/settings_screen.dart` (both are reachable in the app; not dead code). Each branches on `providerData` to pick the right re-auth path (`password` needs a password prompt + `EmailAuthProvider`; `google.com` / `apple.com` need their own re-auth + `deleteGoogleAccount()` / `deleteAppleAccount()`; anonymous needs neither). If you touch one, check the other — they've drifted out of sync before (that's how the Google-account deletion bug was found while adding Apple).
